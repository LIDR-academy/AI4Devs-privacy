# 3. Casos de uso prácticos en LLMs

En esta sección se describen escenarios reales y técnicamente viables en los que la tokenización y la anonimización se aplican específicamente dentro de flujos con modelos de lenguaje (LLMs), distinguiendo infraestructura, propósito, restricciones y riesgos.

---

## 3.1 Tokenización + APIs externas (LLMs de terceros)

**Objetivo principal:** permitir que el LLM procese información contextual sin exponer datos personales reales al proveedor externo.

**Flujo operativo común (basado en lineamientos PCI y guías de seudonimización GDPR):**

1. El sistema recibe datos sensibles (ej.: nombre, CURP, email, póliza médica).
2. Antes de construir el prompt, se aplica **tokenización** via vault interno o servicio HSM/KMS.
3. El prompt enviado al LLM contiene **tokens significativos** (ej.: `<USER_8742>` o `<CLAIM_ID_512A>`).
4. El modelo produce una respuesta usando los tokens.
5. La aplicación **destokeniza localmente** y muestra el dato real únicamente a actores autorizados.

**Cuándo se recomienda:**

* Atención al cliente supervisada (chatbots).
* Generación de resúmenes de casos legales, médicos o financieros.
* Clasificación de tickets con información sensible.
* Razonamiento semántico donde la identidad es irrelevante, pero la referencia debe permanecer.

**Requisitos prácticos:**

* Token Vault interno o gestionado con HSM/KMS (AWS KMS, GCP KMS, Azure Key Vault, HashiCorp Vault).
* Logging y auditoría del proceso de tokenización/destokenización.
* Políticas de acceso basadas en *least privilege*.

---

## 3.2 Tokenización en LLM locales (on-premise o private cloud)

El proceso es similar al caso API, pero el propósito puede variar:

* **Modo seguridad**: reducir riesgos si los logs del modelo o del pipeline pueden persistir datos.
* **Modo ingeniería**: facilitar entrenamiento o pruebas en ambientes no productivos sin usar producción real.
* **Modo cumplimiento**: segmentación entre áreas, aun cuando el modelo está dentro de la empresa.

**Adicionalmente, posible integración con:**

* **Confidential Computing / Enclaves** (AMD SEV-ES, Intel SGX o Confidential VM de Azure).
* **Data Loss Prevention (DLP)** aplicado a prompts y respuestas.
* **Control de versiones y auditoría** del dataset o prompts de entrada.

---

## 3.3 Anonimización en datasets de entrenamiento (irreversible)

**Objetivo principal:** usar datos de producción para entrenar modelos sin poder reidentificar personas en el futuro.

**Aplicaciones típicas:**

* Entrenamiento para clasificación de tickets en soporte.
* Modelos clínicos para análisis de síntomas sin asociación personal.
* Sistemas tributarios o antifraude donde los patrones son relevantes, pero la identidad no.

**Técnicas relevantes según NIST, ICO y PDPC:**

* Eliminación de identificadores directos (IDs, direcciones, teléfonos).
* Generalización (edad: 33 → grupo 30-35).
* Perturbación estadística y agregación (diferential privacy, buckets de riesgo).
* Medición mediante métricas k-anonymity, l-diversity o t-closeness cuando corresponde.

**Resultado esperado:** el dataset deja de ser considerado **dato personal** sujeto a GDPR **si y solo si** se valida que la reidentificación es improbable según el contexto, no únicamente por la técnica.

---

## 3.4 Diferencias operativas según tipo de uso en LLMs (Inferencia vs Fine-Tuning)

| Tipo de uso                                         | Tokenización                                                          | Anonimización                                      |
| --------------------------------------------------- | --------------------------------------------------------------------- | -------------------------------------------------- |
| **Inferencia** (chat, procesamiento en tiempo real) | Muy útil y recomendado, especialmente con proveedores externos        | Menos práctica, puede perder contexto semántico    |
| **Fine-tuning**                                     | No recomendado si mantiene trazabilidad personal y se comparte modelo | Recomendado y más seguro                           |
| **Evaluación / pruebas**                            | Tokenización útil para ambientes QA/UAT                               | Anonimización para datasets sintéticos o reducidos |
| **Compartición de modelo**                          | Alto riesgo si se tokeniza                                            | Anonimización obligatoria en la práctica           |

**Regla operacional clave:**

* Si el modelo será **compartido, versionado o liberado**, **no usar tokenización** como sustituto de anonimización.
