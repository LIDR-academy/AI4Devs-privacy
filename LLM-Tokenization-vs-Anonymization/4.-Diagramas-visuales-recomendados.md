
# 4. Diagramas visuales recomendados

## 4.1 Introducción y aclaración de acrónimos

Antes de describir los diagramas sugeridos, es necesario aclarar los principales términos y componentes técnicos que se utilizarán, dado que estos son comunes en arquitecturas de privacidad, seguridad criptográfica y flujos de IA empresarial.

| Acrónimo  | Significado                         | Descripción breve y rol en el sistema                                                                                                     |
| --------- | ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **LLM**   | Large Language Model                | Modelo de lenguaje de gran tamaño utilizado para inferencia, completado de texto o entrenamiento. Puede ser local o mediante API externa. |
| **API**   | Application Programming Interface   | Medio por el cual una aplicación consume servicios externos o internos, en este caso, un modelo de IA.                                    |
| **PII**   | Personally Identifiable Information | Datos que permiten identificar directa o indirectamente a una persona (nombre, CURP, IP, biometría, etc.).                                |
| **Vault** | Token Vault / Secure Data Vault     | Repositorio seguro donde se guarda el mapeo token ↔ dato real, protegido con políticas, auditoría y cifrado.                              |
| **HSM**   | Hardware Security Module            | Dispositivo físico de alta seguridad para almacenamiento y manejo de claves criptográficas; evita extracción de llaves.                   |
| **KMS**   | Key Management Service              | Servicio administrado de gestión de claves (ej. AWS KMS, GCP KMS, Azure Key Vault). Puede complementar o reemplazar un HSM.               |
| **DLP**   | Data Loss Prevention                | Sistema que inspecciona y bloquea transmisión no autorizada de datos sensibles en texto, red, correo u otros medios.                      |
| **FPE**   | Format Preserving Encryption        | Cifrado que conserva el formato original del dato (útil para tarjetas, identificadores, CU­RP, RFC).                                      |
| **DP**    | Differential Privacy                | Técnica matemática para anonimización agregada que introduce ruido controlado sin bloquear utilidad estadística.                          |

Estos conceptos serán utilizados de manera coherente en los diagramas descritos a continuación, con el objetivo de facilitar la implementación y auditoría de entornos productivos con IA.

## 4.2 Diagrama 1: Flujo de tokenización para LLM externo vía API (reversible)

**Propósito:** mostrar cómo fluye el dato desde el usuario hasta el modelo externo, sin exponer información sensible.

**Componentes clave a incluir en el diagrama:**

1. **Front-end / cliente** (navegador, app móvil, chatbot).
2. **Servicio backend interno** (control de negocio y validación).
3. **Módulo de tokenización** con acceso restringido a **Token Vault + HSM/KMS**.
4. **DLP / Sanitization Layer** previo al envío al proveedor.
5. **API Gateway corporativa** con logging controlado.
6. **Proveedor de LLM (OpenAI, Claude, Gemini, etc.)**, sin acceso a datos reales.
7. **Módulo de destokenización interno** únicamente en la capa final de presentación autorizada.
8. **Registro y auditoría** aislado y sin trazas de datos personales.

**Notas de implementación recomendadas:**

* La destokenización solo debe ocurrir **después** de recibir la respuesta y en un contexto con privilegios mínimos.
* El vault no debe estar accesible desde la capa lógica del LLM ni desde el cliente.
* Se debe incluir un **ciclo de rotación de tokens** basado en políticas internas (inspirado en PCI DSS).

## 4.3 Diagrama 2: Arquitectura para LLM local con cifrado y enclaves seguros

**Propósito:** proteger datos aún cuando el modelo se ejecuta en infraestructura controlada.

**Elementos que el diagrama debe incluir:**

1. **Enclave de ejecución seguro** (Intel SGX / AMD SEV / Azure Confidential VM).
2. **Modelo LLM local o fine-tuned** dentro del enclave.
3. **Servicio de cifrado/descifrado** con llaves gestionadas por **HSM o KMS**.
4. **DLP local + monitor de logging** (no debe persistir contenido sin limpieza).
5. **Control de acceso basado en RBAC/ABAC**.
6. **Canal seguro TLS interno** entre microservicios.

**Punto crítico:**
Incluso con modelos locales, pueden existir fugas vía **logs, memory dumps, backtracking y observabilidad APM**, por lo que se requiere un pipeline estricto sin almacenamiento de contenido crudo.

## 4.4 Diagrama 3: Proceso de anonimización irreversible para dataset de entrenamiento

**Propósito:** documentar el ciclo correcto de transformación y validación de anonimización.

**Componentes obligatorios en el diagrama:**

1. **Dataset crudo** con PII.
2. **Clasificación de campos**: directos, cuasi-identificadores, sensibles y contextuales.
3. **Motor de anonimización** con reglas basadas en:

   * generalización
   * supresión
   * agregación
   * perturbación
   * métricas k-anonymity / l-diversity (cuando aplicables)
4. **Evaluación de riesgo de reidentificación** (no es solo transformación).
5. **Dataset anonimizado** con Certificación Interna de Uso.
6. **Política de destrucción o sellado del dataset original**.

---

## 4.5 Diagrama 4: Decisión operativa entre tokenización y anonimización (árbol de decisiones)

**Objetivo:** ayudar a arquitectos y responsables de datos a escoger la técnica adecuada.

El diagrama debe incluir las siguientes rutas lógicas:

Pregunta 1 — ¿Se necesita recuperar el dato original?

* Sí → Tokenización (o cifrado + tokenización)
* No → pasar a Pregunta 2

Pregunta 2 — ¿El uso es para analítica, investigación o entrenamiento?

* Sí → Anonimización irreversible
* No → pasar a Pregunta 3

Pregunta 3 — ¿El dato será procesado en un sistema o proveedor fuera del control corporativo?

* Sí → Tokenización o eliminación del identificador
* No → evaluar riesgo residual + arquitectura local segura
