# 5. Ejemplos técnicos sencillos

Los siguientes ejemplos son ilustrativos, realistas y basados en patrones operativos alineados con buenas prácticas de privacidad, seguridad y arquitectura. **No contienen datos ni escenarios ficticios irreales** y **no pretenden reemplazar validación legal ni de cumplimiento específico**.

---

## 5.1 Ejemplo en un sistema web (PHP/JavaScript) con tokenización reversible

**Objetivo:** permitir que el backend procese información sensible sin enviar datos reales al LLM externo.

**Flujo resumido:**

1. El usuario envía un formulario con nombre, correo y descripción.
2. El backend detecta campos PII.
3. Se tokeniza antes de construir el prompt.
4. El LLM procesa únicamente tokens.
5. El backend destokeniza solo cuando es estrictamente necesario.

**Pseudo-implementación (PHP + Vault API interna)**

```php
// Ejemplo educativo, no productivo.

$inputName = $_POST['name'];
$inputEmail = $_POST['email'];
$inputMessage = $_POST['message'];

// Llamar a servicio interno de tokenización
$tokenizedName = TokenService::createToken($inputName);
$tokenizedEmail = TokenService::createToken($inputEmail);

// Construir prompt SIN PII
$prompt = "Clasifica el siguiente ticket. Usuario: $tokenizedName, Correo: $tokenizedEmail, Texto: $inputMessage";

// Enviar a LLM externo
$response = LLMClient::sendPrompt($prompt);

// Destokenizar solo en capa segura
$result = str_replace([$tokenizedName, $tokenizedEmail], [$inputName, $inputEmail], $response);

echo $result;
```

**Buenas prácticas asociadas:**

* La **tokenización nunca debe ocurrir en frontend**, sino en un **servicio backend autorizado**.
* Se recomienda usar **Hashicorp Vault + HSM / KMS** para almacenamiento del mapeo.
* El log debe registrar solo tokens, nunca PII.

## 5.2 Ejemplo para prompts (transformación controlada)

Cuando se integra LLM vía prompts directos (CLI, SDK o asistentes internos), la regla es:

**Nunca enviar PII tal cual** — usar tokens y mantener **consistencia semántica**.

Ejemplo de prompt incorrecto:

```
Analiza el perfil del cliente Juan Pérez, correo juanperez@gmail.com y dime si está en riesgo.
```

Ejemplo aplicando tokenización simbólica:

```
Analiza el caso del sujeto <CLIENT_339A>. Información: historial de pagos, comportamiento mensual y notas internas. Indica probabilidad de riesgo. No solicites más datos personales.
```

Si el sistema requiere mostrar resultados asociados a la persona real, la **destokenización se realiza en backend controlado**, **nunca en el cliente** ni en el **LLM**.

## 5.3 Ejemplo para modelos locales (fine-tuning seguro y entrenamiento)

**Objetivo:** permitir que el modelo aprenda patrones sin conservar trazabilidad personal.

En vez de entrenar con datos como:

```
2023-10-11, paciente María López, 32 años, diagnóstico: Diabetes tipo II, nota: fatiga crónica
```

Aplicar **anonimización irreversible estadística**:

```
2023-Q4, grupo de edad: 30-35, género: F, condición crónica: Diabetes Tipo II, síntoma general: fatiga recurrente
```

**Razones técnicas según NIST IR 8053 e ICO:**

* Se elimina identificador directo (nombre).
* Se reduce precisión de atributos cuasi-identificadores (fecha → trimestre, edad → rango).
* Se conserva **utilidad analítica** mediante atributos clínicos relevantes.

Si el modelo requiere granularidad individual sin PII, se puede usar **identificadores sintéticos no reversibles** (UUID generados aleatoriamente sin tabla de mapeo).

---

### Conexión con decisiones de arquitectura

| Caso                                       | Técnica recomendada        |
| ------------------------------------------ | -------------------------- |
| Sistema CRM operativo                      | Tokenización               |
| Soporte automatizado vía LLM externo       | Tokenización + DLP         |
| Dataset para entrenamiento                 | Anonimización irreversible |
| Modelos internos compartidos entre equipos | Anonimización              |
| Auditoría interna cifrada                  | Tokenización + HSM/KMS     |

---

### Riesgos si no se aplica correctamente

1. El LLM podría almacenar o reproducir texto con PII accidentalmente.
2. El log, APM o herramientas de observabilidad podrían capturar el texto plano.
3. Reidentificación por correlación entre datasets, incluso si se “eliminó el nombre”.

En estos casos, la **seudonimización NO equivale a anonimización** y sigue siendo dato personal según GDPR (Recital 26).
